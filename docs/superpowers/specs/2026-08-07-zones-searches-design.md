## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Источник данных зон | Сгенерировать из открытых данных (api.hh.ru/metro + GeoJSON районов), скрипт в репе | Свежие станции (БКЛ, МЦД) и координаты руками не собрать без ошибок |
| Охват | Линии 1–12 + БКЛ + МЦК + МЦД D1–D4 (станции в границах Москвы); все районы старой Москвы, включая безметрошные (ближайшие станции); Новая Москва районами не входит | Ответ пользователя; станции Сокольнической/Троицкой в Новой Москве всё равно попадут через свои ветки |
| Хранение справочника | Только в памяти: JSON в репе → `embed` → пакет `zones`. Таблицы `zones` и FK нет | Конечные статические данные; двух мест хранения и синхронизации не нужно; пересечения удобнее в Go |
| `visible_people` | SQL-функция в Postgres, `LANGUAGE sql STABLE` | Буквально «единая функция» из §4; инлайнится планировщиком; одна точка на уровне БД |
| Секции/вердикты пула | В Go, не в SQL | Пулы маленькие, формула покрывается табличными юнит-тестами |
| Пересечение зон одного юзера | **Правила нет вообще** — любые зоны, лимит только «≤3 активных» | Решение пользователя (спека §2.1/§8/§11/§13 обновлена): «Хамовники» + «красная ветка» — разные намерения; точный дубль UI и так не предлагает |
| Ошибки | HTTP 400 + код в конверте (`search_limit`, `unknown_zone`, `invalid_field`) | Как в онбординге |

## 1. Справочник зон

Файл `moscow.json` в пакете `zones`, в бинарь через `embed`. Два уровня:

- **`stations`** — атомарная единица `{id, name}`. Платформа на линии:
  Киевская-кольцевая и Киевская-АПЛ — разные станции.
- **`zones`** — всё, что выбирается в пикере, `kind`:
  - `line` — ветки: 1–12, БКЛ, МЦК, D1–D4 (только станции в границах Москвы);
  - `station` — зона «у метро»: одноимённые платформы пересадочного узла
    склеены в одну зону («Киевская» = все три платформы);
  - `district` — районы старой Москвы; станции внутри + на границе;
    безметрошным — ближайшие станции соседних районов.

Поля зоны: `id`, `kind`, `name`, `name_in` («в Хамовниках» / «на оранжевой
ветке» / «у метро Сокол»), `name_gen` («Хамовников» — для «пул Хамовников»),
`stations[]`. Склонения — готовые строки в файле, никакой рантайм-морфологии.
У веток `name` — разговорное имя цветом («оранжевая»), официальное — подписью.

`id` — стабильные слаги (`d-khamovniki`, `line-11`, `st-sokol`): они навсегда
вморожены в `searches.zone_id`. Зоны из справочника не удаляются.

**Генерация** — скрипт `tools/genzones` (остаётся в репе — прогнать снова,
когда откроют станции): линии и станции с координатами из открытого датасета,
границы районов — открытый GeoJSON; станция → район по point-in-polygon плюс
буфер ~400 м для приграничных; безметрошные районы — ближайшие станции по
центроиду. Результат вычитывается руками и коммитится; скрипт одноразовый по
режиму запуска, но версионируемый.

**Пакет `zones`**: `Load()` из embed с fail-fast валидацией (битые ссылки на
станции, дубли id, пустые зоны, пустые склонения); `Get(id)`,
`Intersects(a, b)`, `Intersecting(id) []string` — последнее и есть граница
пула для SQL (`WHERE zone_id = ANY($1)`).

## 2. Схема БД — миграция `0002_searches.sql`

```sql
searches(
  id uuid PK DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users(id),
  zone_id text NOT NULL,              -- слаг справочника, без FK
  price_min int NULL,                 -- «от» опционально
  price_max int NOT NULL,             -- «до» обязательно (§2.1)
  rooms_min int NULL, rooms_max int NULL,
  move_in date NULL,                  -- месяц заезда, первое число месяца
  term text NULL CHECK (term IN ('half_year','year','open')),
  has_stuff text[] NOT NULL DEFAULT '{}',
  status text NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','paused','closed')),
  close_reason text NULL
    CHECK (close_reason IN ('found_here','found_elsewhere','changed_mind')),
  pool_seen_at timestamptz NOT NULL DEFAULT now(),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CHECK ((status = 'closed') = (close_reason IS NOT NULL)),
  CHECK (price_min IS NULL OR price_min <= price_max),
  CHECK (rooms_min IS NULL OR rooms_max IS NULL OR rooms_min <= rooms_max)
)
-- индексы: (user_id); частичный (zone_id) WHERE status='active'
```

**Лимит «≤3 активных»** — в сервисе, в транзакции с `SELECT … FOR UPDATE`
строк юзера (против гонки двойного создания). Один и тот же метод проверки для
create / edit / reactivate: реактивация обязана перепроверять слоты.

**`pool_seen_at`** — бейдж «M новых»: при создании `now()` (выдачу зоны только
что видел); «новые» = люди пула, чей поиск создан позже отметки; открытие
экрана пула ставит `now()`. Известная неточность: человек, попавший в пул
правкой зоны старого поиска, в «новые» не попадёт (по `updated_at` было бы
хуже — любая правка цены делала бы его «новым» для всех).

**`blocks`** — `(blocker_id, blocked_id, created_at, PK(пара))`. Создаётся
сейчас пустой: кнопка блока — шаг 8, но `visible_people` учитывает таблицу с
первого дня. Запись направленная (кто нажал), действие обоюдное.

**`visible_people`** — той же миграцией:

```sql
CREATE FUNCTION visible_people(viewer uuid) RETURNS SETOF uuid
LANGUAGE sql STABLE AS $$
  SELECT c.id FROM users c, users v
  WHERE v.id = viewer AND c.id <> v.id
    AND c.status = 'active'
    AND (v.gender_pref = 'any' OR c.gender = v.gender)
    AND (c.gender_pref = 'any' OR v.gender = c.gender)
    AND NOT EXISTS (SELECT 1 FROM blocks b
      WHERE (b.blocker_id = v.id AND b.blocked_id = c.id)
         OR (b.blocker_id = c.id AND b.blocked_id = v.id))
$$;
```

Статус смотрящего не проверяется намеренно: draft и pending имеют право
листать (§5); правило — про то, кого видно.

## 3. Зонный пул (пакет `pools`)

Выборка: Go берёт `zones.Intersecting(Z)`, SQL отдаёт активные поиски
`zone_id = ANY($ids)` от людей из `visible_people($viewer)` с данными
мини-карточек. Секции и вердикты — Go.

Если у человека несколько поисков пересекают Z — карточка одна, лучший
результат (полное > частичное > не совпали).

**Чипы по параметрам** (его поиск против моего):

| Параметр | ✓ зелёный | «краем» жёлтый | серый |
|---|---|---|---|
| цена (`min`=NULL → 0) | вилки пересеклись с запасом | касание границей (35–45 и 45–55) | не пересеклись |
| комнаты | так же, вилки | так же | так же |
| заезд (месяц) | тот же месяц | соседние месяцы | дальше |
| срок | равные | соседняя ступень (полгода+↔год+, год+↔бессрочно) | полгода+↔бессрочно |

Не указан у него → бледный чип «не указана», в секциях не участвует.
Не указан у меня → параметр не участвует вовсе.
«Пересёкся» для секций = зелёный ИЛИ жёлтый.

**Секции** (§2.1, поверх чипов; жёсткие — цена и заезд):
- **полностью** — все указанные обоими параметры пересеклись
  (цена участвует всегда: `price_max` обязателен);
- **частично** — не полностью, но цена или заезд пересеклись;
- **не совпали** — и цена, и заезд мимо.

Инвариант: в «Совпали по всем» не бывает серого чипа.

Сортировка в секциях — свежесть поиска; хвост «не совпавших» — топ-20.
Без своего поиска — одна секция без чипов, сортировка «заполненность
параметров, потом свежесть». «N совпадений анкеты» — счётчик равных полей из
9 (schedule, smoking, pets_own, pets_ok, noise, guests, cleaning, alcohol,
expenses); скор совместимости отложен (§9).

**Счётчики** — `PromoCounts(viewer, zone, params)` →
`{people, full_match, avatars, new_count}`. Зовут: промо-блок выдачи (params
из формы, не сохранённые), карточки «Моих поисков» (params поиска), пустая
зона (people=0). Тот же код, что секции — расхождение счётчиков исключено по
построению.

## 4. HTTP API

Всё под `tma`-авторизацией, ошибки — конверт `httpx` с кодами.

| Ручка | Что делает |
|---|---|
| `GET /api/v1/zones` | справочник целиком: байты embed-файла, ETag по версии; пикер ищет на клиенте |
| `GET /api/v1/feed?zone_id&price_max&…` | выдача без сохранения: `{promo: {people, full_match, avatars, my_search_id?, slots_used}, points: []}` — `slots_used` нужен состоянию промо «слоты заняты 3 из 3»; точки пустые до шага 5 |
| `POST /api/v1/searches` | создать; 400: `search_limit`, `unknown_zone`, `invalid_field` |
| `GET /api/v1/searches` | карточки: параметры + `people/full_match/new_count` + `points_count: 0` |
| `PATCH /api/v1/searches/{id}` | правка параметров/зоны, та же валидация |
| `POST …/{id}/close` | `{reason}` — одна из трёх причин §3 |
| `POST …/{id}/reactivate` | из архива, с перепроверкой слотов |
| `GET /api/v1/pools/zone/{zone_id}` | секции пула; сайд-эффектом `pool_seen_at = now()` моему поиску зоны |

Слои `handler → service → storage`, интерфейсы на стороне потребителя — как в
`users`.

## 5. Сидер

`cmd/devseed`, идемпотентный (фиксированные `tg_id` от 900000001, апсерт):
~20 фейковых активных анкет — разнообразие по полу/`gender_pref`/привычкам,
одна фото-заглушка на всех в photostore, поиски веером вокруг Хамовников и
красной ветки: все три секции, «краем», «не указана», обоюдная половая
невидимость. Без сидера пул руками не проверить.

## 6. Тесты

- юнит `zones` на реальном файле: валидность ссылок, уникальность слагов,
  склонения непусты, `Intersects` симметрично, станция ветки пересекает свой
  район;
- юнит `pools` таблично: все строки таблицы чипов, NULL-края, касание границ,
  соседние месяцы, формула секций, инвариант «в полном нет серого»;
- DB: `visible_people` (пол обоюдно, блок в обе стороны, draft/pending
  невидимы), лимит `searches` под гонкой, интеграционный пул на сиде.
