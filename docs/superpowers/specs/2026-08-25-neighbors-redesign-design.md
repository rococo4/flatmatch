# Редизайн: подбор «Соседи», вкладка «Лайки», выключение рыночных квартир — дизайн

Дата: 2026-08-25. Статус: решения согласованы в чате по макетам
(https://claude.ai/code/artifact/2271b036-3b81-4523-892e-cde93c079a53,
страница «Подбор · светлая» — источник вёрстки и микрокопии). Причина:
отзывы посева — «список людей без квартиры непонятно что делать», «слово
„пул" непонятно»; решение — карточный подбор вместо списков и лент.

## Решения

| Вопрос | Решение |
|---|---|
| Структура | Табы: **Соседи · Лайки · Поиски · Профиль**. Слово «пул» уходит из интерфейса целиком; рабочее имя механики — «подбор», в коде — deck |
| Подбор | ОДНА колода на все активные поиски смотрящего: люди (ищут соседа) и комнаты («к себе») вперемешку; человек в подборе один раз (дедуп по человеку) |
| Жесты | Свайп вправо / сердце = дорогой лайк (5/24ч, как сейчас); свайп влево / стрелка = пропустить; тап по карточке — полная анкета (у комнаты: тап по карточке — анкета квартиры, тап по строке автора — его анкета) |
| Пропуск | `passes(user_id, target_id, created_at)`: цель — человек ИЛИ точка; пропущенный скрыт из подбора 7 дней, потом возвращается сам; «Показать пропущенных · N» в конце подбора стирает все passes смотрящего разом |
| Сравнение | По ЛУЧШЕЙ паре «мой поиск × его поиск» среди пересёкшихся зонами: выше секция → больше зелёных чипов → мой более свежий поиск. Карточка целиком про эту пару: бейдж зоны, бейдж «совпали по всем параметрам», вердикт-чипы. То же правило — в саммари мэтча (вместо «первого активного») |
| Порядок подбора | По секции лучшей пары (полное → частичное → нет), внутри секции свежие вперёд; комнаты ранжируются по цене доли против моей вилки (в вилке → полное, иначе → нет; «заезд» в ранжировании не участвует — решение по ревью) |
| Видимость | «Мы увиделись» (§2.3) не меняется: подбор виден только с активным поиском. Режим «посмотреть без подписки» УМИРАЕТ: кнопка формы — «Сохранить и смотреть», просмотр = подписка. pending/draft: листать и пропускать можно, сердце серое (лайк 403 как сейчас), сверху жёлтая плашка |
| Лайки | Отдельная вкладка с бейджем непросмотренных: плитки 2 в ряд — фото, имя, бейдж зоны на фото («ищет: Арбат» розовым / «на твою комнату» зелёным + зелёная рамка плитки), ✓-чипы совпавших параметров лучшей пары; сортировка по совпадению, без слов. Тап → анкета лайкнувшего со стрелкой (отклонить) и сердцем (взаимно, бесплатно) |
| Отклонение лайка | = пропуск: та же строка passes на человека, входящий скрыт 7 дней, сам лайк НЕ трогается (сгорание — только удаление мэтча и блок, §2.3); «Показать пропущенных» возвращает и их |
| Фильтры | Шторка «Каким должен быть сосед» из «Соседей» и «Лайков»: кого показывать (ищут соседа / зовут к себе), возраст от–до, животные в квартире (без животных / не против моих), курение (не курит совсем / не курит дома), режим дня (сова / жаворонок), чем занят (учится / работает / не работает). Мультивыбор, пусто = неважно; серверные параметры deck-запроса, на клиенте — localStorage; видимость они НЕ меняют (не visible_people) |
| Рыночные квартиры | ВЫКЛЮЧАЮТСЯ (этап 1 — спрятать, не вычищать): парсер остановлен, точки type=flat закрыты, весь их UI и дешёвый лайк убраны; код, таблицы и данные остаются до этапа 2 (отдельная сессия после 2–3 недель посева) |
| «К себе» | Остаётся и живёт в подборе карточкой комнаты: зелёная шапка «Комната · сосед уже живёт там» (или «заезжает»), фото комнаты с пейджером, факты (метро, «Твоя доля N ₽ [+ счётчики]», комната/изолированность), НОВОЕ поле «описание» (текст ≤ 400, модерация вместе с фото), чипы ограничений; строка автора внизу. Сердце = «Хочу эту комнату» (дорогой лайк автору, как сейчас) |
| Фото анкеты | До 5, первое — главное (обложка карточки). Сетка в анкете и в шаге онбординга: добавить/удалить/перетащить порядок. На проверку набор уходит только при ДОБАВЛЕНИИ фото; удаление и перестановка одобренного набора статус не трогают (решение по ревью); статус один на анкету, отдельные фото не помечаются |
| Анкета | «Чем занимаешься?» += вариант «Не работаю» (код `none`). Вопрос про траты переформулирован: «Как делить общие расходы — коммуналку, бытовое?» → «Поровну и сразу» / «Записывать траты (Splitwise и т.п.)» / «Разберёмся по ходу» (коды не меняются, только лейблы/вопрос) |
| Пустые состояния | Без поиска: «С кем будешь жить?» + «Найти» + «Как это работает» (3 шага) + «Где уже ищут» (тап → форма с зоной → «Сохранить и смотреть»). Конец подбора: «Пока все» + «Показать пропущенных · N» + «Сохранить ещё поиск · слот K из 3» |
| Пуши | `zone_new`, `liked`, `matched`, `still_searching`, `post_match`, вердикты, `point_ping` для «к себе» — живут; `pool_new`, `point_gone`, пинг рыночных — умирают вместе с квартирами. Диплинк `zone_new` ведёт в «Соседей» |

## 1. Схема — миграция 0013_neighbors.sql

```sql
ALTER TABLE users DROP CONSTRAINT users_occupation_check;
ALTER TABLE users ADD CONSTRAINT users_occupation_check
    CHECK (occupation IN ('study', 'office', 'hybrid', 'remote', 'shift', 'none'));

ALTER TABLE users ADD COLUMN photo_keys text[] NOT NULL DEFAULT '{}';
UPDATE users SET photo_keys = ARRAY[photo_key] WHERE photo_key IS NOT NULL;
ALTER TABLE users DROP COLUMN photo_key;

ALTER TABLE points ADD COLUMN description text NULL CHECK (char_length(description) <= 400);

CREATE TABLE passes (
    user_id    uuid NOT NULL REFERENCES users (id),
    target_id  uuid NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, target_id)
);
```

- имя CHECK оccupation уточнить по факту (`\d users`), в 0001 он анонимный —
  тогда `DROP CONSTRAINT` по реальному имени.
- `photo_keys`: первый элемент — главное фото (обложка). Ключи файлов
  остаются `photos/<uuid>.<ext>`, но теперь `photos/<user_id>-<n>.<ext>`
  ЛОМАЛ бы порядок — ключ каждого фото генерируется со случайным суффиксом
  (`photos/<user_id>-<8hex>.<ext>`), порядок хранит только массив.
- `passes.target_id` без FK: цель — users.id ИЛИ points.id (uuid-ы не
  пересекаются); чистка — вместе с этапом 2.
- Пропуск «протухает» чтением: `created_at >= now() - interval '7 days'`
  скрывает, старше — игнорируется; «Показать пропущенных» = `DELETE FROM
  passes WHERE user_id = $1`.

Закрытие рыночных точек — не миграция, а одноразовый SQL при выкатке
(контроллер): `UPDATE points SET status = 'closed', close_reason = 'closed',
edited_at = now() WHERE type = 'flat' AND status <> 'closed'`.

## 2. API

### Фото анкеты

- Любое ДОБАВЛЕНИЕ → `photo_status = pending`; удаление/перестановка статус не трогают. `POST /api/v1/me/photos` (multipart `photo`) — добавляет в конец;
  >5 → 400 `photo_limit`. `DELETE /api/v1/me/photos/{index}` — убирает
  (последнее нельзя, если анкета когда-либо отправлялась: фото обязательно,
  §4 — 400 `last_photo`). `PUT /api/v1/me/photos/order` `{"order":[2,0,1]}` —
  перестановка (перестановка индексов, 400 иначе). Любая из трёх операций →
  `photo_status = pending` (у active/draft; логика Submit/enqueue как в §5
  сейчас). Старый `POST /me/photo` умирает.
- DTO `Profile`: `photo_url` → `photo_urls: string[]` (свои — все всегда);
  чужие карточки: `photo_urls` одобренного набора (пока pending у active —
  по правилу §5 «заглушка», т.е. пустой массив). Аватар = первый элемент.
- Модератору — альбом (sendMediaGroup) или первое фото + «и ещё N» (решает
  имплементер по возможностям Bot API, вердикт один на набор).

### Подбор

- `GET /api/v1/deck?who=people,rooms&age_min=18&age_max=30&pets=none,ok_mine&smoking=no,outside_only&schedule=owl&occupation=study,working,none`
  → `{"cards":[...]}`, до 50 карточек в порядке подбора.
  Карточка: `{"kind":"person", person: {user_id, name, age, occupation,
  last_seen, photo_urls[], habits-поля, about}, pair: {zone: zoneDTO,
  zone_match: bool, section: "all|partial|none", chips: [{param, verdict}],
  params: paramsDTO (его лучшего поиска)}}` ИЛИ `{"kind":"room", point:
  {id, stage, zone, price_share, utilities, isolated, rooms, bathrooms,
  description, restrictions[], photo_urls[], responses, author: {user_id,
  name, age, photo_urls[], habits…}}, pair: {...}}`.
  Выборка: люди — как PoolCandidates по ВСЕМ зонам моих активных поисков,
  дедуп по человеку, лучший вердикт; комнаты — активные intent_home в тех
  же зонах. Исключаются: я сам, смэтченные, уже лайкнутые мной, passes
  моложе 7 дней, невидимые (visible_people). Фильтры — WHERE по анкете
  (`occupation`: `working` = office/hybrid/remote/shift; `pets`: `none` →
  pets_own='none', `ok_mine` → pets_ok='ok'; `smoking`: `no` → 'no',
  `outside_only` → in ('no','outside')). Требует активного поиска — иначе
  200 с `{"cards":[], "no_search": true}`.
- `POST /api/v1/people/{id}/pass` и `POST /api/v1/points/{id}/pass` → 204,
  upsert в passes (обновляет created_at). `DELETE /api/v1/me/passes` → 204,
  и ответ `{"restored": N}`.
- `GET /api/v1/feed`, вход в пул квартиры (`POST /points/{id}/enter` и
  выход), голоса свежести — УДАЛЯЮТСЯ из роутера (410 не нужен, клиент один).
  `GET /zones/top` живёт (люди). Промо-эндпоинты пула — удаляются.

### Лайки

- `GET /api/v1/likes/incoming` дополняется: у каждого — `pair` (лучшая пара
  против МОИХ поисков; у лайка «на твою комнату» — бейдж комнаты), сортировка
  по секции/чипам; исключает passes моложе 7 дней.
- Отклонить = `POST /people/{id}/pass` (тот же), фронт после него перечитывает
  список. Ответный лайк — существующий `POST /likes` (бесплатный).

### Формы

- Поиск: как есть (`POST/PUT /searches`), «look»-режима на фронте больше нет.
- «К себе»: `POST /points` intent_home += `description`; валидация ≤400;
  модерация — фото + описание + цена (как §5).

## 3. Выключение рыночных квартир (этап 1)

- `docker-compose.yml`: сервис parser — `profiles: [off]` (не поднимается);
  код парсера не трогаем.
- Роутер: убрать `GET /feed` (или переключить фронт целиком на /deck и
  удалить), маршруты пула/входа/выхода/голосов flat-точек, `POST /points`
  для type=flat (создание «Присмотрел квартиру»), шеринг диплинков
  `point_<flat>` отвечает 404 (точки закрыты — уже так).
- Воркеры свежести: пинг/TTL/скрытие — гейт по «есть живые flat» станет
  no-op после закрытия точек; intent_home пинг остаётся. Код не удалять.
- Фронт: все экраны/куски про рыночные квартиры удаляются (FeedScreen
  points, FlatPool*, PointForm для flat, блок «Присмотренные» в Поисках,
  голоса «живая/сдана»). «К себе» форма и экран остаются.
- CLAUDE.md: §2.2/§8 сжимаются до «к себе» + пометка «рыночные квартиры
  выключены (этап 1), код заморожен до этапа 2»; §12 — шаг 11.

## 4. Фронт — структура

- `TabBar`: 4 вкладки (Соседи/Лайки/Поиски/Профиль), бейдж непросмотренных
  лайков на «Лайках» (число), бейдж новизны на «Поисках» как сейчас.
- Новые экраны: `DeckScreen` (карточка + жесты + кнопки + точки лимита +
  фильтры), `FiltersSheet`, `LikesScreen` (плитки), `LikerProfileScreen`
  (анкета + стрелка/сердце), `DeckEmptyScreen` (первый заход: интро 3 шага +
  «Где уже ищут»), `DeckEndScreen`, `PhotoGrid` (анкета/онбординг).
  Свайп — pointer events руками (без библиотек): порог ~35% ширины,
  вращение ±8°, отмена возвратом; кнопки дублируют жест.
- Переиспользуются: PersonProfileScreen (тап по карточке), HomePointView
  (тап по комнате), SearchParamsScreen (кнопка «Сохранить и смотреть»,
  режим look удалён), MySearchesScreen (без блока квартир), MatchScreen,
  ProfileEditScreen (+фото-сетка), OnboardingScreens (фото-шаг → сетка,
  вопрос трат, «Не работаю»).
- «Лайки» перестают жить в Профиле («Тебя лайкнули» уходит из
  MyProfileScreen; «Мои мэтчи» остаются).
- Вёрстка и микрокопия — со страницы «Подбор · светлая» холста, дословно.
  Тёмная тема — уже существующие токены, ничего нового.

## 5. Тесты

- Go: deck-запрос (дедуп по человеку, лучшая пара — секция/чипы/свежесть,
  passes 7 дней, фильтры, исключения смэтченных/лайкнутых, комнаты в общем
  порядке, `no_search`); passes (upsert, протухание, полная очистка);
  photos API (лимит 5, last_photo, порядок, photo_status → pending);
  incoming с pair и сортировкой; occupation none; description валидация.
- Фронт: tsc/lint/build; свайп — ручная приёмка на стенде.
- Приёмка на проде: два аккаунта — подбор с двух сторон, лайк/пропуск/
  возврат пропущенных, отклонение лайка, взаимный, комната в подборе.

## Не входит (этап 2 и позже)

подписки» с замыленными карточками; ротация/анти-матфей в подборе; undo
свайпа; пуш «пропущенные вернулись»; сохранение фильтров на сервере.
