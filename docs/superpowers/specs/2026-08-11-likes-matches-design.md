# Профиль → дорогой лайк → мэтч — дизайн (§12 шаг 4)

Дата: 2026-08-11. Статус: согласован в брейншторме; пользователь разрешил
переход в план без ревью спеки (ночной режим).

Охват: бэкенд (миграция, likes/matches, API) + фронт-проводка четырёх готовых
экранов + приёмка. Петля продукта замыкается на сидированных данных.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Сброс лимита 5/день | СКОЛЬЗЯЩИЕ 24 часа: слот возвращается через 24ч после траты; «следующий через N ч» показываем |
| Ответный лайк | Любой лайк при существующем встречном входящем — бесплатен и без требования поиска, каким бы путём в UI ни ставился |
| Бейдж «Тебя лайкнули · N» | Все неотвеченные входящие; отметки «просмотрено» нет — висит, пока не ответишь |
| Контакты без username | Deep-link tg://user?id=… + честная подсказка «если не открылось — он напишет тебе первым» |
| Рождение мэтча | В транзакции лайка (вариант А) |

Отклонения от ориентира §11 (внести в спеку):
- таблицы `like_budget` НЕТ — бюджет считается окном по `created_at`
  spent-лайков (частичный индекс);
- колонки `status` у лайка НЕТ — «в мэтче» выводится из `matches`.

## 1. Схема — миграция 0003_likes.sql

```sql
likes_users (
    from_id, to_id uuid NOT NULL REFERENCES users(id),
    zone_id  text NULL,   -- контекст пула; у ответного может быть NULL
    point_id uuid NULL,   -- заготовка шага 5, пока всегда NULL
    spent    boolean NOT NULL,  -- тратил ли слот; решается в момент вставки
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (from_id, to_id),
    CHECK (from_id <> to_id)
);
CREATE INDEX likes_users_to_idx ON likes_users (to_id);
CREATE INDEX likes_users_budget_idx ON likes_users (from_id, created_at)
    WHERE spent;

matches (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    a_id, b_id uuid NOT NULL REFERENCES users(id),
    context_zone_id  text NULL,  -- копия контекста ПЕРВОГО лайка пары
    context_point_id uuid NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    CHECK (a_id < b_id)
);
CREATE UNIQUE INDEX matches_pair ON matches (a_id, b_id);
```

`spent` восстановить задним числом нельзя (после мэтча встречные есть у обоих),
поэтому только флаг в момент вставки. `created_at` несёт окно бюджета,
`next_free_at` (старейший spent в окне + 24ч) и выбор «первого лайка».

## 2. Транзакция лайка (сервис likes)

Как сделано (Task 2, `likesrepo`):

```
1. лок ПАРЫ: SELECT id, status FROM users WHERE id IN (from, to)
   ORDER BY id FOR NO KEY UPDATE
   — сериализует бюджет (урок шага 3: лочить родителя; проверки отдельными
     стейтментами на READ COMMITTED) И пару целиком;
   — лока одного from НЕ ХВАТАЕТ: одновременные взаимные лайки тогда не видят
     друг друга ни на каком уровне изоляции, оба решают «встречного нет» и
     в базе остаются два односторонних лайка БЕЗ мэтча;
   — общий порядок по возрастанию id — то, что спасает зеркальные транзакции
     от дедлока;
   — статус from читается тем же стейтментом (гейт шага 2).
2. from.status = 'active'? нет → ErrNotApproved (403): в draft и pending можно
   листать и сохранять поиски, но не ставить дорогие лайки (§5). Гейт стоит
   до всего остального: ответить draft'у некому — visible_people его прячет.
3. to ∈ visible_people(from)? нет → entity.ErrNotFound (404, не раскрываем)
4. встречный входящий to→from существует? (reply)
   свой исходящий from→to уже существует? (already — повторный тап)
5. НЕ reply и НЕ already → проверки траты:
   есть активный поиск? нет → ErrNeedSearch (400 need_search)
   count(spent за 24ч) >= 5 → ErrLikeLimit (400 like_limit + next_free_at)
   — при already проверки пропускаются: повтор ничего не тратит, иначе второй
     тап по пятому за сутки отвечал бы «лимит», а не «уже лайкнуто»
6. INSERT лайка, spent = НЕ reply, ON CONFLICT (from_id, to_id) DO NOTHING
   (повторный тап → 0 строк → идемпотентно «уже лайкнуто», контекст первого
   тапа не перезаписывается)
7. reply → INSERT мэтча: least/greatest пара, контекст ОЛДЕСТ-лайка пары,
   ON CONFLICT DO NOTHING + перечитать. Только при reply: под локом пары это
   единственное состояние, где обе строки лайка точно есть, а «already без
   reply» вставил бы мэтч из ОДНОГО лайка.
8. КОММИТ. Если мэтча нет — добор вне транзакции (settledMatch): взять тот же
   лок пары и перечитать мэтч. Встречный лайк, идущий прямо сейчас, держит лок
   до конца, поэтому добор встаёт к нему в очередь и обе стороны возвращают
   один и тот же мэтч.
9. Budget(from) — остаток и next_free_at по окну.
```

Инвариант, который держит лок пары: «обе строки лайка есть ⇒ мэтч есть».

Добор (шаг 8) — best-effort, а не гарантия: если встречный лайк стартовал уже
ПОСЛЕ того, как добор отпустил лок, первый лайкнувший честно вернёт
`matched: false` — мэтч к тому моменту ещё не существует. Он приедет ему в
«Мои мэтчи»/«Тебя лайкнули» (и пушем, шаг 6); ровно один мэтч на пару и
`spent` только у первого лайка гарантированы всегда.

Лимит 5 — `entity.MaxDailyLikes`. Требование поиска: ЛЮБОЙ активный (§2.3 —
skin in the game, не гео-проверка).

## 3. API

| Ручка | Ответ |
|---|---|
| `GET /people/{id}?zone={zone_id}` | профиль через visible_people (невидим → 404): имя, возраст, фото, занятость, анкета енумами, «о себе» (только одобренное), `shared[{field,value}]`, контекст-зона, `liked_me`, `my_like`, `budget{remaining,next_free_at}` |
| `POST /likes {to_id, zone_id?}` | `{matched, match_id?, budget}`; 400 `need_search` / `like_limit`(+`next_free_at`); 403 `not_approved` (§2 шаг 2); 404 |
| `GET /likes/incoming` | неотвеченные входящие, свежие сверху: карточка + зона контекста + `not_searching` (§2.3 серая пометка) + `at`. Бейдж = длина списка |
| `GET /matches` | список: match_id, пир (имя, возраст, фото), контекст, дата |
| `GET /matches/{id}` | ЕДИНСТВЕННОЕ место контактов: `username`, `tg_id` + саммари: ГДЕ (зона), ПО ПАРАМЕТРАМ (пересечения вилок конкретикой), ПО АНКЕТЕ (совпавшие поля) |

Приватность структурно: username/tg_id ни в одном другом DTO; чужие лайки
видит только адресат; «сейчас не в поиске» — вычисляется по отсутствию
активных поисков лайкнувшего.

Саммари мэтча: контекст-зона историческая (из мэтча), пересечения параметров
и анкеты — живые на момент просмотра.

## 4. Фронт

1. Тап по карточке пула → живой PersonProfileScreen (`user_id` + зона пула в
   query): совпадения зелёными «вы оба…», «о себе», MainButton «Хочу жить
   вместе · 3 из 5»; `liked_me` → тон «Ответить — мэтч сразу» + «не тратит
   лимит»; `need_search` → форма поиска с возвратом на профиль.
2. `matched: true` → экран «Это мэтч» (fetch `/matches/{id}`), «Написать
   @username» или deep-link с подсказкой.
3. «Тебя лайкнули»: живой список, «Ответить» = тот же POST; бейдж таба —
   длина incoming.
4. «Мои мэтчи» в своём профиле → детали мэтча.

## 5. Тесты

- DB: гонка взаимных (барьер, ровно один мэтч, оба matched); бюджет под
  гонкой (6 параллельных → 5 spent); ответ бесплатен/без поиска; окно 24ч
  (25-часовой spent не считается); visible_people-гейт (пол/блок → 404);
  идемпотентность повтора; next_free_at.
- Юнит: выбор контекста первого лайка, shared-поля, расчёт budget.
- Приёмка в браузере: лайк → лимит → ответ → мэтч на сидах (dev-юзер ↔ сиды:
  сидам нельзя «ответить» из UI — им лайки проставляются psql'ом для
  сценария входящих).

## Не входит

Пуши (шаг 6); `point_id`-контекст и «Хочу эту комнату» (шаг 5);
авто-протухание входящих и сортировка по совпадению (§9); блок (шаг 8);
пост-мэтч опрос (шаг 6-7).
