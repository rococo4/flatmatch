# Редактирование анкеты, мультивыбор в поиске, удаление мэтча — дизайн

Дата: 2026-08-22. Статус: решения согласованы в чате (макет B выбран,
семантика удаления/блока выбрана), ждёт ревью Арсения.

Охват: три независимых изменения одним шагом сборки — (1) наборы вместо
вилок в комнатности, сроке и месяце заезда поиска; (2) отдельный экран
редактирования анкеты (список «вопрос → ответ» со шторкой) вместо прохода
по онбордингу; (3) удаление мэтча любой стороной и блок из мэтча.

## Решения

| Вопрос | Решение |
|---|---|
| Что множественно | Комнатность, срок, месяц заезда — наборы. Зона одна на поиск (§2.1 не меняется), бюджет — вилка |
| Пустой набор | «неважно», совпадает со всем (как NULL сегодня) |
| Совпадение наборов | Пересечение непустое → ✓ зелёный; пустое → серый; «краем» у наборов нет (остаётся только у цены) |
| «4+» | Хранится как 4; значения комнат 1–4; в лейблах 4 = «4+» |
| Старые поиски | Миграция разворачивает вилки в наборы: `[min..max]` с потолком 4, `NULL`-сторона = край диапазона; `term` → `{term}`; `move_in` → `{move_in}` |
| Редактирование анкеты | Отдельный экран (макет B): фото и «о себе» сверху, ниже строки «вопрос → ответ ›», строка открывает шторку с вариантами онбординга, выбор сохраняется сразу. Онбординг по шагам остаётся ТОЛЬКО для первого заполнения (draft) |
| Что на проверку | Как §5: фото и «о себе» — по кнопке «Отправить на проверку», остальное — молча и сразу |
| Удалить мэтч | Любая сторона, без согласия второй и без пуша: строка `matches` и ОБА лайка пары стираются, люди снова видят друг друга в пулах и могут лайкнуть заново; потраченные слоты не возвращаются |
| Блок из мэтча | = удалить мэтч + блок. Блок из ЛЮБОГО места (профиль, мэтч) также стирает мэтч и лайки пары — одно правило, не два |
| Спека | §2.3 «мэтч необратим» → «мэтч живёт, пока его не удалит одна из сторон»; §9: гашение лайков при удалении мэтча и блоке — единственное разрешённое; §5: блок стирает мэтч, «Контакт недоступен» остаётся только для бана |

## 1. Мультивыбор параметров поиска

### Схема — миграция 0011_search_sets.sql

```sql
ALTER TABLE searches
    ADD COLUMN rooms          int[]  NOT NULL DEFAULT '{}',
    ADD COLUMN terms          text[] NOT NULL DEFAULT '{}',
    ADD COLUMN move_in_months date[] NOT NULL DEFAULT '{}';

UPDATE searches SET
    rooms = CASE
        WHEN rooms_min IS NULL AND rooms_max IS NULL THEN '{}'
        ELSE (SELECT array_agg(DISTINCT least(n, 4) ORDER BY least(n, 4))
              FROM generate_series(coalesce(rooms_min, 1), least(coalesce(rooms_max, 4), 4)) n)
    END,
    terms = CASE WHEN term IS NULL THEN '{}' ELSE ARRAY[term] END,
    move_in_months = CASE WHEN move_in IS NULL THEN '{}' ELSE ARRAY[move_in] END;

ALTER TABLE searches
    DROP COLUMN rooms_min, DROP COLUMN rooms_max, DROP COLUMN move_in, DROP COLUMN term,
    ADD CONSTRAINT searches_rooms_range CHECK (rooms <@ ARRAY[1, 2, 3, 4]),
    ADD CONSTRAINT searches_terms_known CHECK (terms <@ ARRAY['half_year', 'year', 'open']);
```

`rooms_min > 4` сегодня даёт `[min..4]` → `{4}` («4+»), что и означала вилка.
Элементы наборов уникальны и отсортированы — это держит репозиторий при
записи (`sort + dedupe`), а не CHECK.

### Сущности и репо

`entity.SearchParams`: `RoomsMin/RoomsMax` → `Rooms []int`; `Term *Term` →
`Terms []Term`; `MoveIn *time.Time` → `MoveInMonths []time.Time` (первое
число месяца, как сегодня `move_in`). `searchesrepo` и `pointsrepo.memberColumns`
читают/пишут три массива. `entity.SearchParams.Validate`: `rooms ⊆ {1..4}`,
`terms ⊆ enum`, месяцы — первое число, не раньше текущего (правило
`move_in` сегодня, поэлементно); наборы нормализуются (сортировка, дубли).

### Совпадение (`pools/verdicts.go`)

```
setVerdict(mine, theirs):
  theirs пуст  → none   (у него «не указана»)
  mine пуст    → green  (мне неважно)
  пересечение  → green, иначе grey
```

`roomsVerdict`, `termVerdict`, `moveInVerdict` — все три через `setVerdict`;
`edge` остаётся только у цены. Секции (`Compare`) не меняются: жёсткие —
цена и заезд, мягкие — комнаты и срок. `Summary` мэтча «по параметрам»:
пересечение наборов текстом («комнаты: у обоих 2 или 3», «заезд: сентябрь
или октябрь у обоих», «срок: год+ у обоих»); если у одного пусто — строка
«комнаты: тебе неважно, у Кати 2» как сегодня у NULL.

### API

`SearchParams` в `searchesapi`/`poolsapi`/`pointsapi` DTO: `rooms: number[]`,
`terms: string[]`, `move_in: string[]` (элементы «YYYY-MM»); пустой массив =
неважно; `null`/отсутствие поля = пустой. Поля `rooms_min`, `rooms_max`,
`term` и строковый `move_in` исчезают (совместимости со старым фронтом не
нужно — деплой один). Ошибки валидации — `invalid_field` с именем поля.

### Фронт

`SearchDraft`: `rooms: number[]`, `terms: Term[]`, `moveIn: string[]`.
Форма (`SearchParamsScreen`): чипы-переключатели; чип «неважно» активен при
пустом наборе и очищает его тапом; подписи под рядами как на макете («Можно
несколько»). Лейблы (`format.ts`): комнаты — непрерывный набор «2–3 комн.»,
иначе «1, 3 комн.», `{4}` = «4+ комн.», `{1,2,3,4}` = «любая»; месяцы — «сен
или окт» / «сен–ноя» при непрерывности; сроки — «полгода+ / год+». Эти же
лейблы — в чипах выдачи, карточках «Моих поисков», вердикт-чипах пула,
саммари мэтча. Вердикт-чипы наборов — только ✓/серый.

Миграция фронта: `isDraftReady`, `draftToParams`, `paramsToDraft`,
`chipLabel`, `paramChips`, `overlapRow`, карточка поиска, форма, зонный пул
(чипы), мэтч.

### Тесты

Go: `verdicts_test` на наборы (пусто/пусто, пересечение, «4+» против 2–3,
месяцы без пересечения — серый, не edge); `entity.SearchParams` валидация
(дубли, 5 комнат, прошлый месяц); `searchesrepo` round-trip массивов;
миграция — на копии дев-базы проверить разворот вилок (`rooms_min=2,
rooms_max=NULL` → `{2,3,4}`). Фронт: `tsc -b`, build; ручная приёмка формы и
пула на стенде.

## 2. Экран редактирования анкеты

### Экран `ProfileEditScreen` (макет B)

Шапка «Анкета» с «назад». Карточка 1: аватар 72 + «Имя, возраст», кнопка
«Заменить фото» (+ жёлтая метка «уйдёт на проверку», когда фото изменено
и ещё не отправлено), строка статуса фото («на проверке» / «не подошло»);
«О себе» — строка-превью текста со счётчиком, тап → шторка с textarea до
200 знаков и подписью из §4. Карточка 2 «Анкета» — строки `label → value ›`:
Возраст, Пол, С кем готов жить, Занятость, Активен, Курение, Свои животные,
Чужие животные, Звук дома, Гости, Уборка, Алкоголь, Общие траты. Тап →
шторка с заголовком-вопросом (дословно §4) и вариантами в стиле
`ChoiceStep` (радио-список), возраст — шторка с полем числа. Выбор →
`PATCH /me/profile` с одним полем, шторка закрывается, строка обновляется;
ошибка — текст под списком, значение откатывается.

Внизу, ТОЛЬКО когда анкета `active` и `photo_status` или `about_status` =
pending: залитая кнопка «Отправить на проверку» → `POST /me/submit`
(существующий), подпись «Фото и „о себе" уйдут модератору вместе; привычки
уже сохранены». У анкеты в статусе `pending` карточка уже в очереди —
перезалитое фото модератор увидит по `/queue`, кнопки нет. Имя — строка
без стрелки, подпись «из Telegram».

### Входы

«Редактировать» в своём профиле → этот экран. Строка статуса «Фото не
подошло…» / «Текст „о себе" не подошёл…» → этот экран с автооткрытой
шторкой фото / «о себе» (сегодня — шаг онбординга). `view === 'editProfile'`
с `initialStep` и рендер `OnboardingFlow` для не-draft пользователей
убираются. Онбординг (`OnboardingFlow`) остаётся для `status = draft`: первое
заполнение и возврат после реджекта фото у никогда не одобренного (§5).

### API

Не меняется: `PATCH /me/profile` (частичный патч, про-активные правки
молча, `about` → `about_status = pending`), `POST /me/photo`, `POST
/me/submit`. Проверить по тестам, что `PATCH` с одним полем у активного не
трогает `status` и не сбрасывает `photo_status`.

### Тесты

Фронт: `tsc -b`, build; ручная приёмка на стенде — смена привычки видна в
пуле без модерации, смена фото даёт кнопку «Отправить на проверку» и
карточку модератору только по ней.

## 3. Удаление мэтча и блок

### API

`DELETE /api/v1/matches/{id}` → 204. 404, если мэтча нет или вызывающий — не
участник. В одной транзакции: `DELETE FROM likes_users WHERE (from_id, to_id)
IN ((a, b), (b, a))`, `DELETE FROM match_polls WHERE match_id = $1`, `DELETE
FROM matches WHERE id = $1`; после коммита — best-effort
`notifications.FailPendingByContext('match:<id>')` (неотправленный
`matched`/`post_match` не должен звать в удалённый мэтч). Повторный вызов —
404 (идемпотентно по смыслу).

`POST /people/{id}/block` — к существующему: перед вставкой в `blocks` та
же очистка пары (мэтч между ними, если есть, и оба лайка), одной
транзакцией. Блок остаётся идемпотентным.

`likesrepo.Create`: гонок с удалением нет — UNIQUE(from_id, to_id) и
транзакция мэтча как сегодня; после удаления повторный лайк тратит слот
(`spent` решается при вставке по наличию встречного лайка, его уже нет).

### Фронт

`MatchScreen`: под саммари — тихая строка «Удалить мэтч · Заблокировать»
(как «Пожаловаться · Заблокировать» в профиле). «Удалить мэтч» → шторка
«Удалить мэтч с {имя}? Он пропадёт у обоих, лайки сгорят, и вы снова
увидите друг друга в пулах. Отменить нельзя» → красная «Удалить» → `DELETE`
→ назад в «Мои мэтчи» с перечиткой. «Заблокировать» → существующая
`BlockPersonSheet` с дополнительной строкой «Мэтч тоже удалится» → `POST
block` → назад. «Мои мэтчи» и счётчики перечитываются; бейдж входящих —
тоже (лайк второго больше не входящий).

### Спека (CLAUDE.md)

- §2.3: «Мэтч необратим, приватен для пары» → «Мэтч приватен для пары и
  живёт, пока одна из сторон не удалит его: удаление стирает мэтч и оба
  лайка молча, пара снова видна друг другу, слоты не возвращаются».
- §2.3 «Правила жизни лайка»: добавить единственные два способа сгорания —
  удаление мэтча и блок.
- §5: «Блок … После блока профиль цели отвечает 404» + «мэтч и лайки пары
  стираются». «Бан пира или блок пары НЕ стирает мэтч» → только бан:
  «Бан пира не стирает мэтч из списков, контакты скрыты — „Контакт
  недоступен"; блок мэтч удаляет».
- §6 Мэтч: строка действий «Удалить мэтч · Заблокировать». Профиль свой:
  «Редактировать» → экран анкеты списком; описание экрана.
- §2.1 / §3 / §6 / §11: комнатность, срок, заезд — наборы; «краем» только у
  цены; `searches(rooms int[], terms text[], move_in_months date[])`.
- §9: из «ОТМЕНЕНО» убрать «любое сгорание лайков» → «сгорание лайков
  помимо удаления мэтча и блока (выход из пула, изменение точки, закрытие
  поиска) и окно возврата лайков».
- §11 matches: «удаляется любой стороной вместе с лайками пары».
- §12: шаг 10.

### Тесты

Go: `matchesrepo.Delete` (чужой → 0 строк; лайки и опросы стёрты;
повторный → 0); `people.Block` у смэтченной пары стирает мэтч; после
удаления пара видна в `PoolCandidates` и `ActiveZonesVisible`; повторный
лайк после удаления — `spent = true`; хендлер — 204/404. Фронт: `tsc -b`,
build; приёмка на стенде с двумя сидовыми пользователями.

## Не входит

Несколько зон в одном поиске; восстановление удалённого мэтча; уведомление
второй стороне об удалении; история удалений; редактирование точек.
