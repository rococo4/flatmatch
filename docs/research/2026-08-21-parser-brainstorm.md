# Брейншторм 7b: парсер ТГ-каналов + LLM + досыпка — развилки и рекомендации

Дата: 2026-08-21. Входные: ресёрч каналов (docs/research/2026-08-20-parser-channels.md),
спека (§8, §10, §11, §13), код api (миграции 0004/0006/0008, points/validate.go,

по каждой развилке — варианты, трейд-оффы, рекомендация. Принятые решения уходят в §13.

## Факты из кода, на которых стоят решения

Всё проверено по репе 2026-08-21, эти инварианты — не мнение, а текущее поведение:

- `entity.Point.Votable()` = `type == flat && url_norm != NULL`. Точка без url_norm
  **не голосуется вообще** — краудсорс-свежесть §8 для неё выключена. §8 при этом
  явно описывает скрытие голосами для tg_channel («сразу closed/gone»), и
  `pointsrepo.Vote` это реализует (source != user_link → closed/gone с первого
  порога). Вывод: спека ждёт, что у tg_channel-точек url_norm заполнен.
- `pointsapi/dto.go`: `out.URL = *p.URLNorm` — «ссылка на оригинал» на карточке
  берётся только из url_norm. Другого носителя ссылки нет (§11 это фиксирует).
- `pointsrepo.Expire` закрывает `closed/expired` **все** active/paused точки с
  `last_seen_alive < now()-14д` — фильтра по source нет. tg_channel-точка живёт
  максимум 14 дней, если её не трогают голоса «да».
- `pointsrepo.PointsForPing` фильтрует `created_by IS NOT NULL AND (source='user_link'
  OR type='intent_home')` — tg_channel/manual **никогда не пингуются**. Менять не надо.
- `points/validate.go`: зона точки обязана быть `kind == station` (313 зон вида
  `st-sokol` в moscow.json). Районы и ветки для точек не годятся — парсер мапит
  только на станции.
- `normalizeURL` (validate.go): только avito.ru/cian.ru, срез www./m., https,
  без хвостового «/», путь обязателен. Дедуп с user_link работает только при
  байт-в-байт той же нормализации — портировать в Python как есть.
- Частичный уникальный индекс `points_url_norm_active` (`WHERE status <> 'closed'`):
  вставка дубля живой ссылки падает — дедуп на уровне БД уже есть.
- `photo_keys text[] NOT NULL DEFAULT '{}'` — пустой массив валиден на уровне БД;
  «≥1 фото» — валидация только пользовательской формы. Ключи фото точек:
  `points/<uuid><ext>` (service/points/service.go), хранилище — photostore.Dir
  (PHOTO_DIR, дефолт ./.data/photos), URL собирается на отдаче (/media/<key>).
  В docker-compose у api **нет volume под фото** — попутный факт: фото сейчас
  живут в слое контейнера и не переживают пересборку; общий volume для парсера
  заодно чинит это.
- `MinPrice=20_000`, `MaxPrice=300_000`, `RoomsCap=20`, `MaxPointPhotos=10`.
- close_reason `gone` уже в словаре кода (rejected/gone/expired/found) — новая
  причина закрытия не нужна.
- Пуш-типы (0008): нового типа «появилась квартира в зоне» нет — и в §7 его нет.
  Парсер не рождает уведомлений вовсе.

## A. Транспорт

**Вариант 1 — HTTP-поллинг t.me/s/ (рекомендуется).** 12 из 15 каналов ресёрча
отдают веб-превью; все 5 стартовых — отдают. Без аккаунта, без SIM, без session-файла,
стек — httpx + HTML-парсер. Ограничение: лента показывает только ~20 последних постов,
поэтому **пропажа поста из ленты ≠ удаление** (мог просто выпасть из хвоста).
Удаление детектируется не лентой, а страницей конкретного поста:
`t.me/<канал>/<id>?embed=1` у удалённого поста отдаёт маркер ошибки
(`tgme_widget_message_error` / «Post not found»). Это покрывает «пост удалён →
точка гаснет» из §13 чистым HTTP. Оговорка: поведение embed для удалённых постов
надо руками верифицировать в первый же день (входит в DoD задачи 1); если маркер
ненадёжен — гашение остаётся на TTL 14 дней и голосах, MTProto как отложенный апгрейд.

**Вариант 2 — MTProto (Telethon).** Полная история, события удаления/редактирования,
фото в оригинале. Цена: прогретый аккаунт на реальной SIM, api_id/api_hash,
session-файл в volume, ненулевой риск бана, FloodWait-этикет. Всё это ради глубокой
истории, которая нам не нужна (нужен только свежий хвост), и детекции удалений,
которую закрывает embed.

**Вариант 3 — гибрид.** Старт на HTTP, модуль `fetch` с двумя функциями
(`feed(channel) -> posts`, `post_alive(channel, id) -> bool`) — естественный шов,
за которым MTProto-реализация появится, если embed подведёт или каналы massово
выключат превью. Это не отдельная работа, а способ написать вариант 1.

**Режим поллинга:** лента каждого канала — раз в 15–30 мин с джиттером (5 запросов
за тик — ничто); проверка живости постов активных tg_channel-точек — раз в 3–6 ч,
по одному запросу в 2–3 сек (верхняя оценка активных точек ~100–200 → минуты работы).
Честный User-Agent, backoff при не-200, канал без превью — лог и пропуск тика.
Риск блокировки на таких объёмах ничтожен.

**Рекомендация: вариант 1 в форме варианта 3 — HTTP-поллинг лент + embed-проверка
удалений, узкий модуль fetch как шов для MTProto потом.**

## B. Язык/рантайм и таблицы

**Python (рекомендуется).** Заглушка уже Python (parser/main.py, Dockerfile
python:3.13-alpine, compose под профилем); html-парсинг (beautifulsoup4/selectolax),
anthropic SDK и psycopg — зрелые; если гибрид А дозреет до MTProto, Telethon не
потребует смены языка. Зависимости: httpx, beautifulsoup4, psycopg[binary], anthropic.

**Go.** Единый стек — но выгода мнимая: сервис общается с бэком только через БД,
общего кода нет by design (§10), а MTProto-библиотеки Go хуже. Переписывание
заглушки ради единообразия не окупается.

**Таблица `channel_posts` — нужна.** Причины: идемпотентность (не скармливать пост
LLM повторно каждый тик — это деньги), аудит (почему поста нет в ленте: skip_reason),
связь пост ↔ точка для гашения, фиксация text_hash под будущие edits. Ориентир схемы:

```
channel_posts(
  channel text NOT NULL,             -- имя канала без @
  message_id bigint NOT NULL,
  posted_at timestamptz NULL,        -- время поста из превью
  text text NOT NULL,
  text_hash text NOT NULL,           -- под детекцию edits (в MVP только пишем)
  photo_urls text[] NOT NULL DEFAULT '{}',  -- cdn-ссылки превью, сырьё
  status text NOT NULL DEFAULT 'new'
         CHECK (status IN ('new','skipped','point_created','error')),
  skip_reason text NULL,             -- 'wanted','room','no_zone','no_price','price_range','dup','forward',...
  llm jsonb NULL,                    -- сырой ответ LLM целиком
  point_id uuid NULL REFERENCES points (id),
  first_seen_at timestamptz NOT NULL DEFAULT now(),
  last_checked_at timestamptz NULL,  -- последняя embed-проверка живости
  deleted_at timestamptz NULL,       -- когда увидели удаление
  PRIMARY KEY (channel, message_id)
)
```

**Миграция — в api/migrations (0009), как у всех.** Одна история схемы, один goose;
парсер свой мигратор не заводит и стартует после api. api таблицу channel_posts не
читает и не пишет — она целиком парсерская, просто живёт в общей схеме.

Что парсеру нужно от существующих таблиц: INSERT в points (+SELECT по url_norm для
дружелюбного дедупа до вставки), UPDATE points (status/close_reason/edited_at при
гашении), SELECT активных tg_channel-точек на проверку живости. users/likes/searches —
не нужны.

**Рекомендация: Python; channel_posts как выше; миграция в api/migrations.**

## C. LLM

**Модель: `claude-haiku-4-5`** ($1 вход / $5 выход за 1M токенов). Задача — короткая
классификация + извлечение из русского поста, это её вес. Объём: ~35 постов/день ×
(~2.5К вход с промптом и справочником станций + ~0.3К выход) ≈ 90К вход / 10К выход
в день → **~$0.15/день, до $5/мес**; справочник станций в системном промпте кэшируется
(prompt caching, стабильный префикс), фактически дешевле. Если качество извлечения
разочарует — эскалация на `claude-sonnet-4-6` ($3/$15) утраивает копейки, решение
обратимое и не архитектурное. Batch API (−50%) не нужен: объём смешной, а латентность
пайплайна проще держать синхронной.

**Ключ:** `ANTHROPIC_API_KEY` в .env → environment парсера в compose. Не в БД.

**Формат: structured outputs** (`output_config.format` / `client.messages.parse()`),
не «попроси JSON в промпте». Схема ответа:

```
{
  "kind": "rent_flat" | "rent_room" | "wanted" | "roommate" | "other",
  "station": "Сокол" | null,        -- ОДНА станция из списка в промпте, ближайшая к жилью
  "price_month_total": 85000 | null, -- ₽/мес за весь объект; «по 40к на двоих» → 80000
  "rooms": 2 | null,
  "isolated": true | null,
  "bathrooms": "combined" | "separate" | "two" | null,
  "utilities": "included" | "meters" | null,
  "deposit": 45000 | null,
  "restrictions": ["no_pets" | "no_couples" | "no_smoking"],
  "move_in": "2026-09-01" | null,
  "listing_url": "https://avito.ru/..." | null   -- avito/cian-ссылка из поста, если есть
}
```

Этаж и площадь отдельными полями не извлекаем — в points их нет; сырой ответ LLM
целиком лежит в channel_posts.llm, задел бесплатный. Классификация:
- `rent_flat` — единственный вид, из которого рождается точка;
- `rent_room` (сдают комнату/подселение) — **отсекать** (skip_reason='room'):
  наша точка flat — объект, который пул снимет вместе; в чужую комнату со-съёмщика
  не зовут, и цены комнат (17–22к) в основном не проходят MinPrice. Считать в
  skip-статистике: если их окажется треть потока — отдельный разговор, не сейчас;
- `wanted` («сниму»), `roommate` («ищу соседа»), `other` — skip. «Ищу соседа»-посты
  в продукт не тащим (§ресёрч: это площадка посева, не контент).

Цена: «по 40к с человека на двоих» LLM приводит к total (промпт-правило);
не восстановилась — null → skip_reason='no_price'. Без метро → station=null →
skip_reason='no_zone'. Диапазон «70–80к» → нижняя граница (честный ориентир, карточка
ведёт на пост).

**Ретраи:** сетевые/5xx — дефолтные ретраи SDK; невалидная схема — один повтор;
после — status='error', пост не блокирует остальные, ручной разбор по таблице.
Фолбэк-провайдер не заводим — при недоступности API посты ждут в channel_posts
со status='new', следующий тик доберёт.

**Рекомендация: Haiku 4.5 + structured outputs + справочник станций в кэшируемом
системном промпте; ключ в env; error-статус вместо хитрых фолбэков.**

## D. Дедуп

Ключевое решение, из которого всё складывается: **url_norm заполняется всегда**.
- В посте есть avito/cian-ссылка → в url_norm кладём её, нормализованную **тем же
  алгоритмом, что validate.go** (иначе дедуп с user_link не сойдётся байт-в-байт).
  Тогда: репост той же ссылки в другом канале — конфликт уникального индекса → skip;
  пользователь позже несёт ту же ссылку → api сам говорит «эта квартира уже есть,
  в пуле N»; «оригинал» на карточке ведёт на Авито (там видно «объявление снято»).
- Ссылки нет → url_norm = `https://t.me/<канал>/<message_id>`. Это даёт: карточке —
  «ссылку на оригинал» (dto уже берёт её из url_norm), краудсорсу — голосуемость
  (Votable требует url_norm), переобработке своего же поста — дедуп через тот же
  индекс. Схема url_norm перестаёт быть «только avito/cian» — фиксануть в §11
  одной строкой при написании спеки.

Межканальный репост без внешней ссылки — у копий разные t.me-адреса, индекс не
ловит. Варианты добора:
1. **Форварды скипать сразу**: превью t.me/s показывает «Forwarded from …»,
   это детерминированный признак — skip_reason='forward' (оригинал придёт из
   своего канала, если мы его парсим; если не парсим — теряем пост, приемлемо).
2. Эвристика (zone_id, price_total, rooms) по живым tg_channel-точкам за 7 дней —
   **только пометка** possible_dup в channel_posts, не блокировка: две разные
   однушки у одного метро за 45к — реальный случай, глушить нельзя.
3. Перцептивный фото-хэш — не делать (объём 10–20 точек/день глазами обозрим).

**Рекомендация: url_norm всегда (avito/cian из поста, иначе t.me-ссылка) + скип
форвардов; эвристика полей — пометка для глаз, не отсечка; фото-хэши — нет.**

## E. Метро → зона

Мапим только на станционные зоны (`st-*`, kind=station — требование, единое с
пользовательскими точками; районы/ветки точкам не даются). Варианты:
1. Fuzzy-матчинг у нас (нормализация + Левенштейн) по свободной строке из поста —
   работает, но дублирует то, что LLM делает лучше (опечатки, «м. Академка»).
2. LLM канонизирует имя, мы мапим exact — LLM может выдать станцию не из нашего
   справочника (МЦД, область, новые станции).
3. **Список станций в системном промпте** (313 имён ≈ 2–3К токенов, кэшируется):
   LLM обязана выбрать из списка или null. Парсер валидирует exact-match по
   нормализованному имени (lower, ё→е, трим) → id зоны. Галлюцинация имени вне
   списка отсекается валидацией.

Пост с двумя метро: LLM выбирает одну, ближайшую к жилью по тексту (промпт-правило);
точка живёт в одной зоне — как и пользовательские. Пост без метро или станция вне
справочника (Химки, МЦД-без-пересадки) → skip_reason='no_zone'; skip-лог — источник
пополнения алиасов, если окажется, что теряем много.

**Рекомендация: вариант 3 — выбор из списка в промпте + exact-match валидация у нас.**

## F. Фото

Превью t.me/s отдаёт картинки постов (cdn telesco.pe, background-image в разметке) —
включая альбомы. Варианты:
1. Хотлинк на CDN Телеграма — ломает модель «в базе ключ, URL собирает хранилище»
  (§11), ссылки протухают, чужой CDN в нашей вёрстке. Нет.
2. Без фото вообще — карточка с плейсхолдером «скрин объявления» уже существует,
   но фото — главный сигнал карточки; терять их при бесплатной доступности глупо.
3. **Качать в photostore** — парсер скачивает до 5 фото (первое в посте — обложка,
   спека допускает до 10 — не жадничаем), проверяет magic bytes (jpeg/png/webp),
   пишет файлами под теми же ключами `points/<uuid>.<ext>` в тот же PHOTO_DIR.
   Технически: общий named volume в compose, смонтированный в api и parser
   (заодно фото api переживут пересборку контейнера — сейчас volume нет вовсе).
   «Общение только через БД» не нарушается: photostore — хранилище, не бэкенд,
   и при переезде на Yandex S3 у парсера будут те же креды и те же ключи.
   Пост без фото → `photo_keys = '{}'` (БД позволяет, валидация «≥1» — только
   у пользовательской формы) → плейсхолдер.

**Рекомендация: вариант 3 — до 5 фото, общий volume, те же ключи; без фото — пусто.**

## G. Жизненный цикл

**Автовалидация до вставки** (иначе skip с причиной): kind=rent_flat; станция
распозналась; 20 000 ≤ price_total ≤ 300 000; rooms null или 1..20; deposit null
или 0..1 000 000; restrictions ⊂ словаря. Это зеркало серверной валидации user_link
минус обязательность фото. Прошла → INSERT сразу `status='active'`, `source='tg_channel'`,
`created_by=NULL`, `zone_id`, url_norm по правилу D, `last_seen_alive=now()` (дефолт).
Пушей о появлении нет — типа такого в §7 нет и не будет.

**Пост удалён** (embed-проверка из A) → `status='closed', close_reason='gone'`,
`deleted_at` в channel_posts. Тихо, без пуша — как TTL-архив в §8 («пуша об архиве
нет»); `point_gone`-пуш остаётся событием голосов, парсер его не рождает. Новая
причина закрытия не нужна: gone = «объявления больше нет», это ровно наш случай.
Закрывать только по однозначному маркеру «поста нет», не по сетевой ошибке/таймауту.

**last_seen_alive: НЕ продлевать парсером.** Развилка честная:
- продлевать, пока пост жив → точки непочищенных каналов (а каналы старые посты
  почти не удаляют) живут вечно при давно сданной квартире; защита — только голоса;
- не продлевать → TTL 14 дней остаётся потолком жизни любой tg_channel-точки.
Ресёрч: рыночные лоты уходят за 1–3 дня; пост, висящий 14 дней, мёртв почти
наверняка, даже если не удалён. 14 дней — правильный гарбадж-коллектор, а живой
человеческий сигнал и так продлевает: голос «да, живая» делает TouchAlive (уже в
коде). Роль embed-проверки при этом — гасить РАНЬШЕ 14 дней, а не держать дольше.
Пинги парсерных точек невозможны by design (PointsForPing фильтрует) — трогать не надо.

**Отредактированный пост:** игнорировать. Редактирования точек в MVP нет (§6/§9),
«точка изменилась»-пуш отменён до пост-MVP; молчаливое обновление цены противоречило
бы будущему правилу «существенное изменение → пуш с дельтой». text_hash в
channel_posts пишем при каждой проверке — когда редактирование появится, детекция
уже будет лежать готовая.

**Рекомендация: сразу active после автовалидации; удалён → closed/gone тихо;
last_seen_alive не продлевать; edits игнорировать, но text_hash фиксировать.**

## H. Досыпка (source='manual')

Кейс: Арсений видит объявление в зоне посева (в ТГ, в чате, на столбе) и хочет
точку в ленте. Оператор — один, объём — единицы в день, инструмент — не продукт.

1. SQL-сиды руками — некуда девать фото, нет валидации, легко насажать битых зон. Нет.
2. CLI в api/cmd (по образцу devseed) — Go-утилита с реюзом zones и валидации, но
   без LLM и без скачивания ТГ-постов; каждый лот пришлось бы набивать флагами руками.
3. Команда в модер-чате бота (/add <ссылка>) — удобно с телефона, но учит api
   скачивать и разбирать ТГ-посты, т.е. переносит парсерскую работу через границу
   сервисов. Нет.
4. **CLI в парсере**: `docker compose exec parser python add.py --url https://t.me/<канал>/<id>`
   — прогоняет пост через весь готовый пайплайн (embed-фетч, LLM, зоны, фото),
   но пишет `source='manual'` и НЕ отсекает по автовалидации молча — печатает
   вердикт и спрашивает подтверждение («цена 18к — ниже лимита, всё равно создать?»
   на старте не нужно: просто печатать отказ с причиной; форсировать нечего).
   Для не-ТГ источников — `add.py --text "..." --photo f1.jpg --photo f2.jpg`:
   тот же LLM-экстрактор по тексту. Гашение досыпанных: manual-точки живут по тем
   же правилам G (голоса, TTL 14 дней), «пост удалён» их касается, только если
   url_norm — t.me-ссылка (тогда парсер проверяет их наравне с tg_channel).

**Рекомендация: вариант 4 — CLI в парсере поверх готового пайплайна; оператор —
только основатель, никакого UI.**

## I. Порядок сборки 7b

1. **Инжест сырья.** Поллер t.me/s одного канала (@arendamsc) → channel_posts,
   идемпотентно; функция post_alive по embed. Миграция 0009. DoD (день 1, стенд):
   два тика подряд дают каждый пост в таблице ровно один раз; embed заведомо
   удалённого поста детектируется как «нет» (руками проверить старый message_id) —
   этим верифицируется транспортный риск A до того, как написан остальной код.
2. **LLM → точки.** Структуризация new-постов, автовалидация, мапинг станций,
   INSERT points active, url_norm по правилу D. DoD: живой канал рождает точки,
   видимые в ленте стенда с зоной/ценой/строкой свежести «добавлена сегодня»;
   у каждого отсеянного поста — skip_reason; повторный прогон не создаёт дублей;
   голос «сдана» по tg_channel-точке закрывает её (существующий механизм, только
   проверить на парсерной).
3. **Фото.** Общий volume в compose, скачивание до 5 фото, обложка. DoD: карточка
   в ленте с фото из поста; пост без фото — карточка с плейсхолдером.
4. **Гашение + проверка живости.** Периодический обход активных tg_channel-точек,
   удалённый пост → closed/gone. DoD: удалённый пост гаснет на стенде за ≤6 ч
   (на стенде — форс-тик руками); точка с avito-ссылкой из поста дедупится с
   user_link-подачей той же ссылки («уже есть, в пуле N»).
5. **Все 5 каналов + досыпка.** Конфиг каналов (env/файл), вежливые интервалы,
   add.py. DoD: за сутки на проде 10–20 точек суммарно; `add.py --url` создаёт
   manual-точку, видимую в ленте.

Отложить за пределы 7b: вторая волна каналов (keystomoscow, lvngrm_msk, гео-фильтр
МО для leavestay/arendamsk_mo), пополнение алиасов станций по skip-логу, любые
метрики кроме `select skip_reason, count(*)`.

## J. Чего НЕ делать (YAGNI)

- MTProto/Telethon и телеграм-аккаунт — пока embed-проверка работает.
- Очереди, redis, вебхуки, реалтайм — тик-поллинг и Postgres, как у пушей.
- Свой мигратор в парсере и отдельный Postgres-юзер с грантами — один VPS, один DSN.
- Пуш «в твоей зоне появилась квартира» — типа нет в §7, не изобретать.
- Реакция на edits постов (обновление цены, пуш дельты) — редактирования точек
  в MVP нет; пишем text_hash и всё.
- Продление last_seen_alive живым постом — см. G.
- Полные фото-альбомы (>5), видео, кружки; перцептивные фото-хэши для дедупа.
- Парсинг комментариев, реакций, просмотров; скоринг «качества» поста.
- «Ищу соседа»-посты как лиды/точки — это площадки посева, не контент (ресёрч §TL;DR-5).
- Автоматический чекер доступности avito/cian-ссылок — уже отложен в §9 со своим триггером.
- Дашборды/алерты парсера — журнал в stdout + SQL по channel_posts достаточно.
- source='realtor' — заготовка остаётся заготовкой.

## Черновик DoD шага 7b (для спеки, после решений по развилкам)

Парсер (Python, отдельный сервис, с бэком только через БД) поллит t.me/s пяти
каналов (@arendamsc, @ugnest_msk, @norealtor, @flats_4_friends, @nebabushkin_msk)
раз в 15–30 мин; сырьё складывает в channel_posts (миграция в api/migrations);
каждый новый пост прогоняет через claude-haiku-4-5 (structured outputs, список
станций в кэшируемом промпте) и посты «сдам квартиру, Москва, станция из
справочника, 20–300к» превращает в points: source='tg_channel', status='active',
created_by NULL, zone_id станционной зоны, url_norm = нормализованная avito/cian-
ссылка из поста, иначе t.me/<канал>/<id> (всегда заполнен: даёт ссылку на оригинал,
голосуемость и дедуп индексом), до 5 фото в photostore через общий volume (первое —
обложка; без фото — пустой photo_keys). Форварды и посты «сниму»/«ищу соседа»/
«комната» отсеиваются с причиной в channel_posts.skip_reason. Раз в 3–6 ч парсер
проверяет живость постов активных tg_channel-точек через embed; пост удалён →
closed/gone без пуша. last_seen_alive парсер не продлевает — TTL 14 дней остаётся
потолком; голоса и «сдана»-порог работают на парсерных точках как на любых.
Досыпка — CLI в парсере (add.py --url / --text) тем же пайплайном, source='manual',
оператор — основатель. Приёмка: на проде 10–20 точек/день из 5 каналов; удалённый
пост гаснет ≤6 ч; avito-ссылка из поста дедупится с пользовательской подачей той
же ссылки; расход LLM ≤ $5/мес.
