# Онбординг end-to-end — дизайн (шаг 2 §12)

Дата: 2026-08-03. Предшественник: шаг 1 «Скелет» (`26408ac`, `22cb1ad`).

Цель: 12 экранов анкеты из §4, путь `draft → отправка → pending`, продолжение
с брошенного шага, редактирование анкеты после одобрения.

Спека продукта — `CLAUDE.md`, источник правды. Решения ниже, расходящиеся с
ней, внесены в неё же тем же коммитом; здесь они помечены как **правка спеки**.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где живёт черновик | На сервере, `PATCH` после каждого шага | Mini App закрывают свайпом; `localStorage` вебвью не гарантирован, а с другого устройства прогресса нет вовсе |
| Обязательность | Все 12 шагов, включая «о себе» | Решение владельца продукта. Риск отвала на шаге 10 принят осознанно |
| Границы шага 2 | Первый проход + редактирование анкеты целиком | |
| Что возвращает на модерацию | Только фото и «о себе» | Ровно то, что модератор смотрит по §5. Правка «сова → жаворонок» не должна выкидывать из пулов |
| Что видно во время перепроверки | Заглушка вместо фото, «о себе» скрыто | **Правка спеки.** Человек остаётся `active` и не выпадает из пулов, непроверенный контент наружу не попадает, теневые колонки не нужны |
| Модель анкеты в API | Плоские колонки + `PATCH` с частичным телом | Шаги не ветвятся и порядок ни на что не влияет — серверная машина шагов защищала бы от непроблемы, а стоила бы вторым путём записи под редактирование |
| Аватар из Telegram | Не используем, фото загружает пользователь | **Правка спеки.** Аватар может быть скрыт настройками приватности, то есть путь всё равно работал бы не у всех |
| Статус ошибки на неполной анкете | `400` + код в конверте | Тела у `submit` нет, так что `422` (про семантику тела) мимо; `409` точнее, но читается как «гонка». Смысл несёт `code`, статус — грубая маршрутизация |

## Данные

Миграция `0002`:

```sql
ALTER TABLE users RENAME COLUMN photo_url TO photo_key;
ALTER TABLE users
    ADD COLUMN about_status text NOT NULL DEFAULT 'pending'
        CHECK (about_status IN ('pending', 'ok', 'rejected')),
    ADD COLUMN onboarding_step smallint NOT NULL DEFAULT 0,
    ADD CONSTRAINT photo_ok_needs_a_file
        CHECK (photo_status <> 'ok' OR photo_key IS NOT NULL);
```

`photo_key` вместо `photo_url` — в базе лежит ключ, URL собирает
`PhotoStore.URL(key)`. Без этого адреса локального стенда запеклись бы в
строки и сломались при переезде на Yandex Object Storage.

`onboarding_step` — закладка «куда возвращать бросившего». Сервер её хранит и
отдаёт, но ничего на ней не строит: порядком владеет фронт.

**Видимость — это рендер, а не выборка.** `User.Visible()` по-прежнему смотрит
только на `status = 'active'`. Поверх этого профиль отдаёт фото при
`photo_status = 'ok'`, иначе заглушку, и «о себе» при `about_status = 'ok'`,
иначе блока нет.

Следствие отказа от теневых колонок: перезалитое фото затирает одобренное.
Отклонили новое — остаётся заглушка, пока человек не загрузит другое. Пуш
«загрузи другое» из §5 становится единственной дорогой назад.

Две ветки реджекта фото:

- ни разу не проходил проверку → `status = draft`, `onboarding_step = 11` (§5);
- активный → статус не трогаем, человек временно с заглушкой.

## API

```
GET   /api/v1/me            профиль целиком
PATCH /api/v1/me/profile    подмножество полей анкеты + onboarding_step
POST  /api/v1/me/photo      multipart, ≤5 МБ, jpeg/png/webp
POST  /api/v1/me/submit     draft → pending, либо 400 со списком незаполненного
```

`PATCH` принимает только поля анкеты — список зашит в DTO, `status` и
`photo_status` через этот вход не проедут. Он же обслуживает редактирование
после одобрения: один путь записи вместо двух.

Ошибки — существующий конверт `httpx.ErrorBody`, к нему добавляется
необязательное поле:

```go
type ErrorDetail struct {
	Code    Code     `json:"code"`
	Message string   `json:"message"`
	Fields  []string `json:"fields,omitempty"`
}
```

Новые коды: `invalid_field` (значение вне перечисления, в `fields` — какое
поле) и `profile_incomplete` (в `fields` — чего не хватает). Оба с `400`.

## Слои

Раскладка как с шага 1: импорты текут внутрь, интерфейсы на стороне потребителя.

**`entity`** — одиннадцать новых перечислений: `Gender`, `GenderPref`,
`Occupation`, `Schedule`, `Smoking`, `PetsOwn`, `PetsOK`, `Noise`, `Guests`,
`Cleaning`, `Alcohol`. У каждого тип, константы и `Parse`-функция по контракту,
заданному на шаге 1: **ошибку не возвращает, нераспознанное даёт `Unknown`**.

Одна функция обслуживает оба направления. На чтении из базы `Unknown` значит
«схема ушла вперёд бинаря» и поле прячется; на записи тот же `Unknown` значит
«клиент прислал мусор» и даёт `400`. Отдельной валидации на вход не нужно.

**`service/users`** — `UpdateProfile`, `SetPhoto`, `Submit`. Правило
`draft → pending` и единственная проверка полноты живут в `Submit`. Там же
ветка для `active`: правка фото или «о себе» сбрасывает соответствующий
`*_status` в `pending`, статус пользователя не трогая.

Проверка полноты предикатом «все обязательные поля не NULL» — ровно в одном
месте, в `Submit`. §5 запрещает другое: выводить этим предикатом *статус*.
Статус остаётся явной колонкой, переход — отдельным действием пользователя.

**`repo/usersrepo`** — один статический `UPDATE` с `COALESCE($n, column)` на
каждое поле, без сборки SQL строками. Ограничение: обнулить поле обратно в
`NULL` таким запросом нельзя. Нам не нужно — все поля обязательны и меняются
только на непустые.

**`photostore`** — интерфейс объявляет `service/users`:

```go
type PhotoStore interface {
	Put(ctx context.Context, key string, r io.Reader, contentType string) error
	Delete(ctx context.Context, key string) error
	URL(key string) string
}
```

Реализация пишет в локальный каталог; `s3.go` появится позже. Подключение
боевого хранилища меняет одну строку сборки зависимостей в `cmd/api/main.go`.
В тестах тот же тип смотрит в `t.TempDir()`.

## Фронт

```
web/src/
├── screens/onboarding/
│   ├── Onboarding.tsx     контейнер: индекс шага, навигация, отправка
│   ├── steps/             12 компонентов по числу экранов §4
│   ├── Final.tsx          развилка: «Анкета готова» + две карточки-пути
│   └── copy.ts            микрокопия §4 дословно
├── screens/profile/       «Профиль свой» + редактирование
└── api/client.ts          + patchProfile, uploadPhoto, submitProfile
```

Навигация — `MainButton` («Далее») и `BackButton` Telegram. Роутер не заводим:
состояния в `App` хватает, `react-router` под 12 шагов и три экрана —
преждевременная зависимость.

Микрокопия §4 не переписывается: спека прямо запрещает «улучшать» её при
сборке. Отдельный `copy.ts` нужен, чтобы расхождение было видно диффом.

Финальный экран собирается по §4 целиком, включая цвета типов. Тап по карточке
ведёт на пустой экран-заготовку — без микрокопии «скоро»; на шагах 3 и 5
заготовка наполнится формой.

## Ошибки и тесты

Go, без базы: `Parse`-функции — только негативные случаи (позитивные повторяют
`switch`); `service/users` против фейкового хранилища — `UpdateProfile`
отвергает значение вне перечисления, `Submit` возвращает список недостающих,
`Submit` у активного сбрасывает `*_status`, а не статус.

Go, под `TEST_DATABASE_URL`: частичный `UPDATE` не затирает соседние колонки;
`CHECK photo_ok_needs_a_file` срабатывает.

Фронт: тестовой инфраструктуры сейчас нет, в этом шаге не заводим.

## Definition of done

- 12 экранов проходятся подряд, ответ каждого уходит на сервер;
- закрыть и открыть Mini App — продолжение с брошенного шага;
- `submit` на неполной анкете отдаёт `400` со списком, на полной — `pending`;
- статус на «Профиле своём» различает `draft` и `pending` разной микрокопией;
- анкету можно отредактировать; правка фото или «о себе» сбрасывает
  соответствующий статус, привычки меняются молча;
- `go build ./... && go vet ./... && go test ./...` зелёные.
